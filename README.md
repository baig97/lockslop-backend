# Lockslop backend

Next.js 16 API, Better Auth OAuth Provider, Drizzle and Neon Postgres.

## Development

Set `.env.local`: `DATABASE_URL` (pooled), `DATABASE_URL_UNPOOLED` (direct), `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `EXTENSION_IDS`, `TYPESAFE_API_KEY`, and `CRON_SECRET`. Never expose these secrets in extension builds. `OAUTH_EXTENSION_CLIENT_ID` is generated by registration if absent.

Run `npm install`, `npm run db:migrate`, `npm run db:seed`, `npm run auth:register-extension`, then `npm run dev`. Registration uses Better Auth’s database adapter in a transaction; it preserves the configured client ID and ensures a link to `${BETTER_AUTH_URL}/api/v1`. Run it once for each backend resource against that environment’s database. Google uses a Web application client with callback `${BETTER_AUTH_URL}/api/auth/callback/google`.

For production registration, supply the production `BETTER_AUTH_URL` and existing `OAUTH_EXTENSION_CLIENT_ID`, and configure `DATABASE_URL` for the production database. Changing the URL alone does not update an existing client’s resource links. Registration prints the client ID and target resource, and does not deploy the backend. The ownerless first-party client is provisioned through the adapter because Better Auth’s client-management endpoints require a signed-in owner.

Auth and OAuth Provider tables live in `auth`; content tables live in `public`. IDs use UUID v4. The extension is a first-party public OAuth client with exact redirect URLs and required S256 PKCE. Dynamic registration and client administration are disabled. Provider-managed opaque access tokens and rotating refresh tokens replace custom handoffs; users must sign in again after migrating. Google browser sessions are separate from extension OAuth tokens. The extension’s browser-managed auth window redirects straight from the signed `/auth/sign-in` entry to Google, with Better Auth verifying the signed query and carrying its state cookies through the redirect.

## Two-stage content pipeline

Both platforms use the same paths. Supported types are `youtube_video` and `linkedin_post`; this backend pass does not implement DOM extraction or extension integration. The old YouTube overview/rating/personal-vote GET routes are retired. Existing authenticated vote PUT and vote-details GET/PUT remain available; auth and stable signal listing are unchanged.

### 1. Cache-only lookup

`POST /api/v1/content/overviews:batch` accepts 1–10 entries:

```json
{"entities":[{"entityType":"youtube_video","url":"https://www.youtube.com/watch?v=abcdefghijk","contentHash":"sha256:<64 lowercase hex characters>"}]}
```

Each entry supplies exactly one nonempty `url` or `externalId`. Overview lookup accepts no content JSON and never calls Jev or any platform API. Bearer authentication is optional and requires `slop:read`; invalid credentials do not silently become anonymous. New identities may be registered, but analysis is never generated during lookup.

Responses contain `results`, in request order. Each item has `index`, the validated `request` (or null for an invalid item), and `status: success | error`. Success includes `overview`: entity UUID/type/nullable identifiers, community vote/reason counts, anonymous or authenticated viewer vote, and a discriminated AI result. Errors have a sanitized `code`, `message` and `retryable` flag. Individual failures do not discard successful items; malformed envelopes and batches outside 1–10 return HTTP 400.

AI states are `ready` (exactly five scores and analysis date), `needs_input` (missing/expired results), `unsupported_language`, and `unavailable` with retryability. Lookup matches the exact entity/hash; it never substitutes another revision's result. Community aggregation remains independent of the hash and excludes private feedback and reports.

### 2. Authenticated derivation

`POST /api/v1/content/ai-signals:derive` accepts the same batch entries plus `content`, requiring the existing Google-backed extension token with `slop:write`:

```json
{
  "entities": [{
    "entityType": "youtube_video",
    "externalId": "abcdefghijk",
    "contentHash": "sha256:<computed digest>",
    "content": {
      "schemaVersion": 2,
      "title": "How bicycle brakes work",
      "description": "A practical explanation of cable tension and brake pad alignment.",
      "publishedAt": "2026-01-01T00:00:00Z",
      "durationSeconds": 240,
      "languageHint": "en",
      "liveBroadcastContent": "none",
      "tags": ["bicycle"],
      "comments": {"status":"available","items":[{"text":"The measured example helped."}]},
      "counts": {"comments":12,"views":100,"likes":null}
    }
  }]
}
```

For LinkedIn, submit the separate strict version-2 schema: `{schemaVersion:2,text,publishedAt,languageHint,comments,counts:{comments,reactions,reposts}}`. There is no title or video duration. Nullable fields default to null, comments to unavailable/empty, tags to empty. Unknown top-level/count fields are rejected; comment item objects retain only text. At most ten comments are accepted. Structured commenter identities are discarded; arbitrary personal information embedded in free text is not guaranteed to be anonymized.

Validation and sanitation precede hashing and entity insertion. Hash recursively key-sorted UTF-8 JSON of `{schemaVersion,entityType,title,description,publishedAt,durationSeconds}` for YouTube or `{schemaVersion,entityType,text,publishedAt}` for LinkedIn. Supplied text is preserved without trimming or Unicode normalization. Comments, counts, tags and language/live hints are outside the hash. `hashContent` uses the same schema/projection as the extension's WebCrypto implementation; `node scripts/sync-contract.mjs --check` in the extension detects drift. Hash mismatches fail before persistence/inference. Sanitized pretty JSON is capped at 32 KiB per entity, lookup bodies at 32 KiB and derivation bodies at 512 KiB. Existing version-1 analyses remain until ordinary pruning; no database migration or cleanup is needed.

Fresh cached results are returned without replacing or retaining another submitted input. On misses, one direct Neon connection holds the batch’s advisory locks for its entity/hash pairs, with a seven-second bounded wait and a bulk cache recheck. Partial lock sets are released before retrying to prevent overlapping batches from deadlocking. The first accepted sanitized input and submitting user are retained, including after failure. Retries use that accepted input. English detection considers YouTube title/description or LinkedIn post text only; non-English or undetermined content returns a cached language result without calling Jev. Missing credentials/provider failure never produce random scores.

Entity resolution, analysis cache reads, pending claims, rate-limit reservations and community reads are batched. All uncached eligible items (up to ten) are evaluated concurrently, then successful results, language outcomes and failures are persisted together using bulk writes in a short transaction. A failed evaluation does not discard other successful evaluations; a failed database commit returns unavailable for all affected generated results. The shared generation pool has ten connections per process, with one connection used per active generation batch rather than per Jev call. Jev evaluates all platform signals in one call (five Score questions for YouTube, seven for LinkedIn), uses a pinned versioned model, normalizes scores by four, and preserves its five-second deadline and restricted retry policy. All signals for an item publish atomically. Each platform has a dedicated context; YouTube's actual video/media remains unseen, while LinkedIn's supplied post text is observable. Both treat comments as unverified supporting evidence and engagement as no evidence of quality. The backend never fetches YouTube or LinkedIn content.

Request limits are 600 overview batches/minute globally, 60 derivation batches/minute per user, and 30 uncached attempts/user/minute plus 120 uncached attempts/minute globally. Model/transport logs omit submitted text, credentials and personal data.

## Identity and storage

Auth remains in `auth`; all content tables are in `public`, with UUID v4 IDs. Entities require exactly one stored non-null identifier. Each identifier is unique per entity type. YouTube URLs and external IDs resolve to the same canonical watch URL. LinkedIn URLs normalize to HTTPS/www without query/fragment and with a trailing slash. LinkedIn external IDs remain opaque separate identities; no alias is guessed from equal activity/content numbers.

`content_analyses` is unique on `(entity_id, content_hash)` and stores first submitting user ID, sanitized JSONB input, status, language outcome, generator provenance, timestamps and expiry. `ai_content_signals` stores five bounded scores linked to the analysis; deletion cascades. There is no `content_payloads` table or provider-revision mechanism. Multiple content hashes coexist; first accepted submissions remain immutable until expiry.

Expiry is one calendar month from first acceptance, for successful, language-gated and failed attempts alike. Expired entries are never served and a new accepted submission can replace them under the lock. `vercel.json` schedules `GET /api/internal/prune-analyses` monthly to delete expired JSON and dependent signals even for never-requested content. Vercel authenticates that route with `CRON_SECRET`; production must define the secret and successful runs must be confirmed in the deployment logs. `npm run content:prune` remains available as a manual fallback. Monthly scheduling can leave expired physical rows until the next run, although API reads exclude them immediately.

Hash/schema validation verifies consistency, not authenticity. Unhashed context can be fabricated even for a valid canonical-content hash. This crowdsourcing risk is explicitly accepted for this milestone. Stored first-submission attribution supports later human review and abuse mitigation; a moderation interface and stronger provenance checks are deferred. No platform-policy compliance claim is made.

## Migration and development cleanup

Migration `0004` removes raw payload retention, replaces signal ownership with analysis IDs and enforces identifier XOR. Existing development content must be cleared first: `npm run content:clear -- --confirm`, then `npm run db:migrate` and `npm run db:seed`. Cleanup fingerprints every auth table (except transient rate-limit counters) and signal definitions before/after inside one transaction; it preserves users, sessions, OAuth clients/tokens and stable signal IDs. This is a deliberate development reset, not a production data migration procedure.

`npm run ai:clear -- --confirm` clears analysis inputs and their scores only. Keep `.env.local` secrets out of source control. `YOUTUBE_DATA_API_KEY` is no longer used and can be removed from backend configuration.

## Verification

- `npm run test:unit`: hashing/sanitation/identity, injected repository cache/failure/concurrency tests, context safeguards and existing TypeSafe transport/response/deadline tests.
- `npm run test:ai`: real Neon constraints, multi-hash cache, expiry, lock deduplication, first-input retention, atomic failures/retries, language gating and retention cascade with a deterministic test evaluator.
- `npm run test:integration`: local HTTP lookup/contribution operations, real OAuth Provider read/write scopes and PKCE regressions, mixed-platform batch derivation via the real handler with a stubbed TypeSafe transport. No platform requests are allowed.
- `npm run test:jev:live`: optional paid Jev generation/persistence smoke test using a derived fixture; temporary content/users are removed.
- `npm run eval:jev`: optional live human-rubric comparison with the historical baseline; scores are evidence strengths, not calibrated detection accuracy.
- `npm run typecheck` and `npm run build`.

Tests clean up their own fixtures. No extension builds, DOM capture, screenshots or actual platform requests are required for this pass. Frontend contract synchronization and integration must happen in the later extension pass.

Generic contribution endpoints use `{entity:{entityType,url},vote}` at `PUT /api/v1/content/my-vote` and `{entity,details}` at `PUT /api/v1/content/my-vote/details`. Read private details with `GET /api/v1/content/my-vote/details?entityType=...&url=...`. Existing YouTube write wrappers remain compatible. LinkedIn source reports are rejected until source resolution is supported.

### Platform signal membership

The single canonical `slop_signals` table is seeded from `lib/contracts/signals.ts`; platform membership is exclusively a code boundary. YouTube retains five keys and LinkedIn independently selects seven, adding `engagement_bait` and `incoherent_reasoning`. AI answer validation, cache completeness and contribution validation enforce the requested entity's membership. LinkedIn's dedicated context follows YouTube's field meanings, five evidence levels, counterexamples, comment ceiling and untrusted-input protections; it does not import/rewrite YouTube signal definitions. Other feedback is not an AI signal.

LinkedIn provenance is `linkedin-signals-v1:<pinned model>`. Older LinkedIn results become cache misses and regenerate from the first accepted input; no bulk deletion is needed. YouTube's formulation provenance is unchanged. Seed adds canonical definitions idempotently without a database migration or replacing existing IDs. Extension presentation descriptions, reason choices and labels are synchronized from the same catalog; its platform weights are independent editable heuristics.

### Privacy consent
Set `PRIVACY_POLICY_VERSION` (currently `2026-10-08`) in deployment environment settings and bump it when publishing a policy that needs renewed acknowledgement. Run `npm run db:migrate` before deploying this change.
`GET /api/extension/privacy-consent` returns the current version and, for a bearer-authenticated user, their saved acceptance. `POST` accepts `{ "version": "2026-10-08", "accepted": true }` using the authenticated account, never a caller-supplied user ID. A stale version returns 409; declining saves the choice and revokes extension tokens and account sessions. Authenticated content endpoints reject missing/outdated consent before processing content. Agreement is requested only after sign-in, in a centered dialog, and functionality resumes after backend confirmation. Anonymous ratings remain available without an agreement prompt.
